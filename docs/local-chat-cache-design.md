# 本地聊天缓存 + 全量检索

2026-07-26 · dashboard

## 问题

两件事，一个根因。

**搜索搜不全。** `chat-find.tsx` 原来对**已渲染 DOM** 做 TreeWalker 扫描，所以它只能看见「已加载窗口」——首屏 60 条，每点一次 load earlier 再加 200。一个 26,874 条消息的会话里，`3/7` 这种计数实际含义是「最近 60 条里的 7 处」，剩下的够不着。跨会话搜索则根本不存在：侧栏那个框只匹配会话标题和 `preview` 字段，服务端也没有任何全文索引。

**打开会话要等网络。** `listMessages` 的结果只在 react-query 的内存缓存里，刷新页面即丢。

## 关键数据

线上实测（193,681 条消息 / 158 个会话 / 原始 JSON 904 MB），按内容块拆开：

| 块类型 | 数量 | 体积 |
|---|---|---|
| `tool_result` | 55,678 | 621 MB |
| `thinking` | 39,956 | 223 MB |
| `tool_use` | 55,678 | 48 MB |
| **`text`（对话正文）** | 42,164 | **11 MB** |
| image / file / interaction | ~2,000 | < 0.5 MB |

**正文只占 1.2%。** 这一个比例决定了整个方案可行：把 900 MB 灌进浏览器不可能，把 11 MB 灌进去毫无压力。增速约 7-10 MB/月。

单会话最多 26,874 条，中位数 390。值得注意的是这 26,874 条里只有 5,779 条含正文——四分之三的消息是纯工具调用回合。

## 方案

两层缓存，分工不同：

**正文层（全量）** — 每台机器每个会话的每条消息，只存 `{id, sessionId, role, createdAt, text}`。约 11 MB，IndexedDB `text` store。搜索只查这一层。

**渲染层（LRU）** — 最近打开的 15 个会话的完整 capped content（工具块、thinking 都在）。让重开会话不必等网络。IndexedDB `full` store，`fullMeta` 记录 LRU 时间戳。

搜索用的数据和渲染用的数据不是一份，这是整个设计的支点：全量正文才 11 MB，而全量渲染内容是 316 MB。

## 为什么是子串扫描，不是倒排索引

语料是中文。MiniSearch / FlexSearch / Lunr 这类库都按空白和标点分词，中文句子会被切成一个巨大的 token，搜「义脑」什么都匹配不到，除非自己塞 bigram 分词器——而 bigram 索引又要多花 2-4 倍原文体积。

线性 `indexOf` 不需要分词器，对 CJK 天然正确，而且和原来的会话内查找语义一致（那个也是 `indexOf`），两个搜索对「什么算匹配」的理解不会打架。

实测：1.49M 字符的语料全扫 **4 ms**，外推到全量 11 MB 约 30 ms。按当前增速还能撑几年。到顶了再换实现——`search-core.ts` 是唯一需要改的文件，所有调用方都是按 hit 表达的，不碰索引结构。

不做 Unicode 归一化：NFKC 能让全角 ＡＢＣ 匹配 ABC，但它会改变字符串长度，而这里每个匹配偏移都要拿去切原文做摘要。精确偏移比模糊折叠值钱。

## 为什么没用 Web Worker

第一版是 Worker，但过不了打包这关：Turbopack（Next 16）不会把 `new Worker(new URL('./x.ts', import.meta.url))` 编译成 worker chunk，而是把 TypeScript 文件原样拷进 `.next/static/media`。浏览器拉到的是裸 TS，解析失败，每次会话都白花一个请求加一条 console 错误才回落。加 `{ type: 'module' }` 也没用（验证方式：看 build 后 `.next/static` 里落的是什么）。

主线程可行，因为两项主要开销都被处理掉了：

- 装载语料分片进行（`db.streamAllText`），几 MB 的 structured-clone 反序列化不会卡在一帧里；
- 扫描本身 10-30 ms，前面还有 120 ms 防抖，属于一次击键的工作量。

而且多数时候根本不用装载：同步引擎边拉边推进内存语料，热标签页里语料已经在了。

## 同步协议

1. `chat.syncProbe` → 每个有消息的会话一行 `{watermark, count, agentName, title, preview}`
2. 和本地比对（`sync-plan.ts` 的 `planSync`，纯函数、可单测）：
   - 本地没有 → 从 0 全量拉
   - 本地 count > 服务端 → 有行被删了，水位线看不见，清掉重拉
   - 水位线或 count 变了 → 从本地水位线拉增量
   - 本地有、probe 里没有 → 会话已删，整个丢掉
3. `chat.syncText` 用 `(updatedAt, id)` 游标分页
4. 行落 IndexedDB，同时推进内存语料

### 三个必须知道的事实

**水位线必须是 `MAX(ChatMessage.updatedAt)`，不能用 `ChatSession.lastMessageAt`。** `api/sync/chat-message/route.ts:36-58` 故意不为 upsert 更新推进 `lastMessageAt`（否则网关重载会把所有会话刷成未读）。而 agent 一个回合里那条 assistant 行是**原地 upsert** 的——内容在变、`lastMessageAt` 不动。拿它做增量同步会漏掉整个正在流式写入的回合。`updatedAt` 是 `@updatedAt`，插入和原地更新都会动，也正是 SSE 流已经在轮询的信号。

**游标必须是 `(updatedAt, id)` 复合，不能只用 `updatedAt`。** 批量插入会在毫秒精度上撞在一起；单用 `updatedAt > since` 会把并列行反复重取，用 `>=` 则永远推不动。

**历史消息实际上是 append-only。** 唯一的 `chatMessage.delete` 路径是 `dequeue` / `clearQueue`（`chat.ts:555,566`），只删未投递的用户排队消息。真正的删除只发生在会话级。所以同步不需要 tombstone 机制，`count` 比对就够了。

probe 成本：`groupBy` 走 `ChatMessage_sessionId_updatedAt_idx` 纯索引扫描，193k 条消息实测 **27 ms**，便宜到可以每 30 秒轮询，不需要为它加任何冗余字段或迁移。

## 跳转到搜索结果

`listMessages` 永远只从最新往回取，所以一个两万条以外的命中根本够不着。新增 `chat.listMessagesAround(sessionId, messageId, before, after)` 返回以某条消息为中心的窗口，形状和 `listMessages` 完全一致（同样过 `capMessageContent`），时间线可以直接渲染。

进入这个「锚定模式」后时间线是**冻结**的：不跟 SSE、不自动滚到底、不追新。顶部有条黄色横幅说明「正在查看历史位置」，点「回到最新」退出并把 `msg` 参数从 URL 抹掉。

锚点滚动分两个循环：等行挂载（WAIT），和挂载后持续校正（SETTLE）。第二个是必要的——markdown 解析、代码高亮、图片拿到固有尺寸，每一样都会把锚点往下推；只在某一帧滚一次，慢设备上消息会停在视野边缘。

## 边界与降级

- **作用域隔离**：数据库名带 workspace 身份（`hermit-chat-cache:<machineId>`，分享链接再加 `::<agentName>`）。切 workspace 就是换一个库，读不到上一个。`pruneForeignScopes` 删掉 keyring 里已不存在的库。这是便利边界不是安全边界——服务端仍按请求的 key 做真正的鉴权。
- **IndexedDB 不可用**（隐私模式、配额、iOS 清理）：全部操作静默返回空，UI 退回服务端行为。
- **失败不缓存**：一次被阻塞的 open（另一个标签页正在升版本）解析为 null，绝不能记住——记住了这个页面余生的缓存就死了。
- **缺 store 自愈**：库存在于当前版本但缺 object store（被别的工具版本无关地打开过、首次升级被打断），`onupgradeneeded` 永远不会再触发，缓存会永久失效。检测到就把版本加一，强制再升一次。
- **写入失败静默**：渲染层写入是缓存行为，配额超了或值不可结构化克隆，必须降级成「下次开会话走网络」，而不是一个未处理的 rejection——后者还会中断链条，把限制存储体积的 LRU 淘汰一起干掉。

## 搜索结果会随缓存增长而收敛

冷启动时同步还在回填，用户已经在搜了。第一次的答案是在部分语料上算的。搜索客户端因此维护一个版本号，语料变化时（节流到每秒一次）通知订阅者重算。

没有这个机制会怎样：搜索结果按查询词记忆化，一次在部分语料上算出的低计数会一直挂在那，直到用户重新输入。**这不是假想的**——实测中一个已缓存 1489 条消息的会话，搜索报告 0 处匹配。修好后同一个查询实测收敛过程：181 → 241 → 388，最终值与独立读取 IndexedDB 得到的计数一致。

## 验证

服务端（对线上真实数据，67 个会话 / 91,576 条消息）：

- `syncProbe` 返回 67 个会话，每行水位线和 agent 齐全
- 最大会话（26,874 条）完整回填：27 页 / 5,779 条正文行 / 2.90 MB / 525 B 每行，无跨页重复
- 中文正文正确抽取（5,779 行里 3,880 行含非 ASCII）
- `listMessagesAround` 锚点居中于 81 行窗口的第 40 位、时间序、无重复；最早一条正确报告 `hasBefore=false`；不存在的 id 返回空

浏览器（同上数据集）：

- 同步确实写入 IndexedDB，全局搜索对中文和拉丁查询都有结果、命中高亮
- 点击结果跳转：URL 带锚点、横幅出现、目标消息滚进视野（687px 视口内位于 229px，即预期的上三分之一）、退出锚定模式清理 URL
- 会话内查找计数覆盖未加载历史：**388 处匹配 vs 当前渲染的 5 处**
- 重开会话在**两个**服务端传输通道都被拦住的情况下 **133 ms 画出 60 行**——只可能来自缓存

单测 30 个（正文抽取、CJK 子串、摘要偏移、同步 diff 规则），typecheck 与 production build 通过，未新增 lint 错误。

## 已知限制

- 全局搜索结果按时间倒序取前 100 条；一个老会话的命中可能被新会话挤出首页。总匹配数是准的。
- 摘要窗口是首个匹配前后各 70 字符；同一条消息里更远的匹配计入总数但不单独高亮。
- ⌘K 从「聚焦侧栏过滤框」改成「打开全局消息搜索」。侧栏那个框只匹配标题，而搜索**说过的话**此前完全没有快捷键。快捷键只在已安装 PWA 里生效，所以侧栏也加了一个放大镜按钮。

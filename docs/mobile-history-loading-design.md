# 移动端历史消息加载 + 防滚动突变

2026-08-22 · dashboard · 待评审

## 症状

手机打开 `dash.swaylab.ai/chat?session=…`：

1. 首屏只有一点点消息。
2. 向上滚动时一次性灌进来一大片消息。
3. 这片消息落地的过程里，视图出现明显的跳动 / 突变。

## 根因（对照代码逐条定位）

**首屏薄。** `INITIAL_WINDOW = 60` 是按「原始消息条数」定的（`app/chat/page.tsx:72`），但时间线已经把四分之三的工具流量折叠成胶囊（`fold-runs.ts`）。60 条原始消息在普通会话里折成约 18 行，工具密集段只有 4 行——手机一屏放不满，看起来就是「一点点」。

**向上滚动一次灌一片。** `use-older-pages.ts` 的 `OLDER_PAGE = 120`（消化后仍是一整页 120 条原始消息），一次 prepend 全部。而且 `app/chat/page.tsx` 的 top-up 效应（内容不足 1.5 屏时自动补页）在手机上几乎必触发，一次最多连拉 5 页。

**突变不是锚点失效，是锚点「没来得及生效」。** `use-prepend-anchor.ts` 的时序是：

```
setRows(整页120条) → React 渲染（markdown 解析 + 代码高亮，同步阻塞）→ 提交 DOM
→ useIsoLayoutEffect 调 reassert() → 浏览器绘制
```

但 `capture()` 在拉取**之前**就把 `until = Date.now() + SETTLE_MS(1500)` 定死了（`use-prepend-anchor.ts:103`）。两个后果：

- 网络回来慢、或者 120 条的解析在手机上耗掉一秒多，等到 `reassert` 真正跑的时候 `Date.now() > until` 已经成立，函数第 56 行直接 `return`——**位置一次都没校正过**，错位的那一帧原样画上去。这就是「跳」。
- 就算赶上了，1500ms 的余量还被同步解析吃掉了大半，图片取到固有尺寸、字体切换这类**异步**生长发生在窗口结束之后，没人再校正，视图再滑一次。

一句话：现在的防跳机制假设「prepend 的解析很快、且 1.5 秒内全部 settle」，在手机上这两条都不成立。

## 新方案

四个改动，按杠杆从高到低排。

### 1. 历史页本地优先：把整段会话预热进 digest 缓存

本地 IndexedDB 已经有三层（`lib/chat-cache/db.ts`），其中 `digest` store 专门存「折叠后时间线要渲染的消化形态」，每行约是完整体的 5%。今天只有 `loadMore` 拉过的那几页会被写进去，warm 也只暖一页（`use-older-pages.ts:211`）。

改动：会话打开后，在 idle 时段、不跟首屏抢资源，从「本地已有最老行」出发，用 `listMessagesBefore` 一页页往回走到会话开头，全部写进 `digest`。节奏照抄同步引擎的「不慌不忙」——每页之间让出事件循环，切会话 / 切后台就 abort。

效果：**重开过的会话，向上滚完全是本地读**，零网络、零等待，页可以很小很碎也不心疼。`summary-paging-design.md` 里 Option A 的测量就是这个支点：会话正文早已在盘上，只是没被历史滚动用上。

### 2. 页面按「渲染行」计，不再按「原始条数」计；页大小减半

把 `OLDER_PAGE` 从 120 降到 60（消化后），commit 时再切成 2 片、每片 30 条。30 条折叠后约 7–10 行正文，markdown + 高亮在手机上约几十到一百多毫秒——**低于一帧预算**，这是下面第 3 条能成立的前提。

首屏薄的问题同样用「行」解决：top-up 从「不足 1.5 屏」改成「不足 3 屏」，且补页走缓存优先 + 分片 commit。冷启动（无缓存）时首 60 条照旧立即画（它是 SSE 窗口，不能动），随后按行补到 3 屏。

页大小和缓存粒度本来就解耦（`pageBefore` 按 `(createdAt,id)` 对行切，不按页对齐），所以改 120→60 不需要清缓存、旧 `digest` 行照用。

### 3. 防跳：把「一次大 prepend」变成「分片 prepend + 每片重锚」

这是直接命中「跳」的那条。改 `use-older-pages` 的 commit：页面到手后（缓存或网络），每片 30 条、`requestAnimationFrame` 间隔，逐片 `setRows`。每片之间 React 会渲染、布局效应会跑、`reassert` 会执行一次——**主线程阻塞被切碎，锚点每片都有机会校正**，最坏位移被限制在一片的高度而不是一整页。

配套改 `use-prepend-anchor`：

- settle 窗口不再从 `capture()` 起算，而是**每片 commit 时重新起算**（`capture` 只记录「读到的位置」，`reassert` 顺带把 `until` 刷新到 `now + 窗口`）。这样网络慢、解析慢都不再吃掉预算。
- 把固定 1500ms 换成「内容上方还在变就一直校正，封顶 3s」：用一个 `ResizeObserver` 盯住锚点行上方的容器，有变化就续，没变化就提前停。图片、字体这类异步生长不再是漏网之鱼。

保留现有的「只校正布局生长、绝不吞掉用户滚动」这条铁律（`prepend-anchor-core.ts`），分片和续窗都只是让它在手机上真正跑得动。

### 4. 预取：读者永远离下一次拉取有一页的距离

现在每次 prepend 完，下一段历史要等用户滚到 seam 才去拉。改动：每 commit 完一页，立刻在 idle 预热**下一页**（现有 warm 逻辑从「只暖一页」改成「始终领先一页」）。配合第 1 条（本地优先），滚动回到已读会话时这个预热甚至是零成本的。

## 落地顺序（可选范围）

- **P0（最小、直接止跳）**：只做第 3 条的前半——分片 commit + settle 按片重算。改动集中在 `use-older-pages.ts` 和 `use-prepend-anchor.ts` 两个文件，不动协议、不动缓存、不动服务端。
- **P1（止跳 + 减量）**：加第 2 条——页大小 60、top-up 按 3 屏、分片 30。
- **P2（滚回几乎全本地）**：加第 1、4 条——整会话 digest 预热 + 领先一页预取。这是体验的天花板，但要跟 30 秒一次的同步引擎、以及 live 窗口的写穿共享同一个 IndexedDB，节奏要小心。

## 验证

- 单元：`prepend-anchor-core` 的「用户滚动 vs 布局生长」不变量继续全绿；新增「分片 commit 不重不漏」的 seam 测试（复用 `use-older-pages.test.ts` 的 `pageBefore` seam）。
- 手机实测：挑一个工具密集会话，冷缓存打开，记录首屏行数（应 ≥ 3 屏）、一次上滑的 commit 片数、以及锚点行在 prepend 前后的视口位移（应 < 1px）。
- 回归：SSE 直播窗口、`listMessagesAround` 锚定模式、`chat-find` 搜索跳转三条路径都不碰本方案，各自照旧。

## 落地结果（2026-08-22，已全部实现）

1. 范围：P0 + P1 + P2 全做。
2. 页大小 60，分片 30（`OLDER_PAGE` / `COMMIT_CHUNK`）。
3. 整会话 digest 预热：单会话上限 `WARM_MAX_PAGES = 20` 批 × `WARM_BATCH = 200` = 4,000 条；淘汰跟着 `FULL_LRU_SESSIONS = 15` 走（预热结束后 `evictFullLru`）。

实现比方案多补了一处：防跳锚点现在区分「读历史」（锚定顶部消息）和「钉在底部」（锚定尾巴），后者用一个镜像的 `planBottomFrame`，保证首屏补页时新历史出现在上方、尾巴不动，而不是把视图甩到刚加载的最顶部。

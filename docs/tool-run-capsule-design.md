# 工具链折叠成一行 · 历史按摘要拉取

2026-08-21 · dashboard

## 问题

一次 agent 回合里，每个工具调用是一条 assistant 消息，每个工具结果是一条 user 消息。
读六个文件跑一次 build 的回合会产生十几条消息，其中没有一条是人说的话。时间线一条消息
一行地铺出来，结果是：**对话读起来像日志，而且往上翻很贵**。

线上库实测（193,681 条消息 / 158 个会话 / `content` 列共 904 MB）：

| 块类型 | 体积 | 占比 |
|---|---|---|
| `tool_result` | 621 MB | 69% |
| `thinking` | 223 MB | 25% |
| `tool_use` | 48 MB | 5% |
| **`text`（对话正文）** | **11 MB** | **1.2%** |

单会话最多 26,874 条消息，其中只有 5,779 条含正文——**四分之三的消息是纯工具回合**。

这两件事是同一个根因的两面：时间线把「怎么做的」和「说了什么」平等对待。

## 方案

### 一、机器动作折叠成一个胶囊

`components/chat/fold-runs.ts`（纯函数 + 14 条测试）把消息流折成三种行：

- **msg** —— 人能读的东西：`text` / `image` / `file` / `interaction`（含 `ask` 问题卡）
- **run** —— 两个 msg 之间所有 `tool_use` / `tool_result` / `thinking`，合成一个胶囊
- **end** —— harness 的「本回合无回复」标记

折叠的单位是**块，不是消息**。一条 `[text, tool_use]` 的 assistant 消息会先出正文行、
再开一个 run；`[tool_use, text]` 则相反。顺序一格不动——只有这样，「两条消息之间」在一条
消息横跨边界时才还是它字面的意思。

`ask` 是唯一不被折叠的 `tool_use`：它本身就是那张问题卡，折进去就等于把一个等人回答的
问题藏起来了。图片、文件下载条同理，永远在外面。

胶囊（`run-capsule.tsx`）折叠时是一行：跑了哪些工具 · 多少步 · 用了多久 · 出错几次。
展开就是原来的时间线——同样的 `ToolChip` / `InlineToolResult`，同样的顺序，一样不少，
只是推迟到你要看的时候。展开的 DOM 只在打开时挂载。

**正在跑的那一个**（时间线最后一行 + 回合在飞）额外显示一条不定量进度条（横向扫光，
`@keyframes run-sweep`）和当前工具名。步数会不会到头是不可知的，所以不做填充式进度条——
那是撒谎；扫光只说明「还在动」，旁边的步数是唯一诚实的量。当前工具名优先取 gateway 的
`activity` 快照：一个跑了四分钟的 Bash 不产生新块，只有快照还是对的。

### 二、历史按摘要拉取

胶囊折叠时只显示工具名、一行参数、错误数。但「load earlier」一直在把整包东西拉下来。

`server/message-digest.ts` 在 `listMessagesBefore` 上加了 `digest` 开关：

| 块 | 摘要后 |
|---|---|
| `text` / `image` / `file` / `interaction` | **原样**（这是对话本身） |
| `tool_use` | 保留 `name` + chip 会显示的那一个参数（≤180 字符） |
| `tool_result` | 保留 `is_error` + 首行（≤180 字符） |
| `thinking` | 只留长度 |

小于 200 字符的块不动——省不下什么，而且不动的块展开时不需要回源。

展开一个摘要胶囊时才调 `chat.getMessages({ ids })` 取那几条的完整内容，一次，之后缓存在
组件里。绝大多数胶囊没人展开，也就永远不花这个钱。

**实时窗口不摘要**：最新 60 条是正在流的、要交互的，保持全保真。摘要只作用于历史。

### 三、往上翻的手感

三处一起改，缺一不可：

1. **每页 60 → 120 条**。两边的预算都变了：字节变成零头，而 120 条原始消息折叠后铺出的
   行数比原来 60 条还少（四分之三是机器动作）。两次往返变成一次。
2. **提前量从 200px 改成两屏**（`pullMargin`）。原来那个 200px 在一次滑动之内——请求
   要等人已经盯着列表尽头才发出去，所以每次手势都以等待收尾。两屏的余量意味着人翻到那里
   时下一页通常已经接上了。这是和原生聊天 app 的差别所在。
3. **摘要页落盘**（IndexedDB `digest` store，DB v3）。第二次翻同一段历史零请求。
   与 `full` 共用 LRU：一个会话从其中一个被淘汰，另一个也一起淘汰。

另加一条**补屏**：实时窗口是 60 条**消息**，折叠后可能只有十几行——会话打开时可能不足
一屏，而不足一屏就没法滚动，也就触发不了上面的预取。所以内容高度不足 1.5 屏时自动补一页，
上限 5 页（一页可能整个折进已有的胶囊里，只长几个像素，不设上限会一路翻到会话开头）。

## 实测

本地跑一个 600 条、按线上比例合成的会话（3/4 是机器动作，`tool_result` 6–11 KB 一条）：

| | 一页 60 条 | 一页 120 条 |
|---|---|---|
| 不摘要 | 191 KB | 376 KB |
| **摘要** | **19 KB** | **38 KB** |

也就是**一页拿到两倍的历史，花五分之一的流量**；折到单条消息是 3.2 KB → 0.32 KB，**十倍**。

浏览器里连着往上翻五次（真实滚轮手势，非脚本调用）：

| | 改前 | 改后 |
|---|---|---|
| 拉回来的消息 | 300 条 | **600 条** |
| 请求数 | 5 | 5 |
| 流量 | ~955 KB | **170 KB** |
| 打开时的行数 | 60 条消息 = 60 行 | 60 条消息 = **24 行** |

展开一个历史胶囊：1 个请求，只取那几条，把完整工具输出补回来。

另外两个没法用数字表达但更重要的：**打开一个会话时最上面看到的是对话本身**，以及往上翻时
下一页在人翻到之前就接上了。

## 取舍

- **摘要页写进 `digest` store，不写 `full`。** 实时窗口的首屏是从 `full` 读的，把裁过的行
  写进去会让某次首屏比上次少东西。
- **胶囊里的 thinking 正文历史里没有。** 展开时和工具参数一起回源。
- **`hasMore` 不从缓存回答。** 手里有整页只证明有历史，不证明缓存有全部历史。
- **summary 模式没动。** 它走本地正文缓存，本来就零请求；折叠之后两者的差别小了很多，
  未来可能可以合并成一个开关。

## 顺手修掉的

`use-older-pages.ts` 的写回路径漏了 `authoredBy`。缓存服务的那一页里，Brain 代说的和
系统 poke 的消息会渲染成人自己打的——这正是 `authoredBy` 当初加进缓存类型要防的事。
